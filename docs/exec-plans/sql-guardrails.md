# SQL Guardrails ExecPlan

## Goal and Non-Goals

Implement a fail-closed generated-SQL guardrail architecture before any model-produced SQL can be executed. The guardrails must parse SQL into a PostgreSQL-aware AST, validate syntax and schema references, block unsafe structures, bound result size and planner cost, execute only through a read-only database role inside a read-only transaction, and expose stable redacted API outcomes.

This plan is intentionally self-contained so a new Codex session can implement it without conversation memory.

Non-goals for this plan:

- Do not change the natural-language retrieval or prompt-ranking strategy except where integration points require passing validation metadata.
- Do not trust provider-declared `tables_used` or `columns_used` as security evidence.
- Do not rely solely on keyword matching. Keyword checks may exist only as supplementary diagnostics after AST parsing.
- Do not implement write-capable SQL, migrations generated by the model, or admin/report-builder escape hatches.
- Do not expose raw provider, parser, or database exceptions to API clients.

## Current Context

The backend currently has a generation-only pipeline:

- `backend/app/services/query_draft.py` normalizes the user question, retrieves schema context through `LexicalSchemaRetriever`, detects several business ambiguities, builds a `SchemaAwarePromptEngine` prompt, calls a `SQLGenerator`, and returns either `SQLGenerationDraft` or clarification.
- `backend/app/api/query.py` exposes `POST /v1/query/draft`, maps provider failures to stable `PublicAPIError` responses, and returns provider SQL directly when structured output is valid.
- `backend/app/domain/sql_generation.py` validates provider output shape with Pydantic, but it does not parse or authorize SQL.
- `backend/app/domain/schema.py` and `backend/app/domain/schema_catalog.py` provide the schema catalog that guardrails must use for table and column validation.
- `backend/app/core/config.py` already configures database connection, provider, retrieval, and prompt settings. Guardrail, EXPLAIN, result-size, and execution settings must be added there.
- `backend/app/db/engine.py` creates the SQLAlchemy engine with connection-level `statement_timeout` and `idle_in_transaction_session_timeout`; generated-query execution still needs per-transaction `SET LOCAL` policy.
- `database/init/20_readonly_role.sh` creates `text_to_sql_reader`, grants `CONNECT`, `USAGE` on `commerce`, and `SELECT` on commerce tables, and sets `search_path = commerce, pg_catalog`. It should be strengthened and tested as part of implementation.
- `text_to_sql/guardrails.py` is a legacy SQLite prototype that uses first-token and forbidden-keyword checks. It is not sufficient for the FastAPI/PostgreSQL backend and should not be used as the security model.

## Threat Model and Trust Boundaries

All generated SQL is untrusted until it passes every guardrail stage. Trust boundaries are:

1. User text enters the API as untrusted natural language. It may contain prompt injection, malicious SQL fragments, sensitive-data requests, or attempts to override system/developer instructions.
2. Schema retrieval and prompt construction use trusted application code and introspected metadata, but the cached `SchemaCatalog` may be stale. Validation must fail closed if referenced objects are missing from the current catalog.
3. Provider output is untrusted even when Pydantic validates the JSON shape. The model can hallucinate identifiers, omit assumptions, emit unsafe SQL, or contradict the prompt.
4. SQL parser output is trusted only when exactly one full PostgreSQL statement is parsed without errors or unsupported syntax.
5. AST policy validation is the primary application authorization boundary. Any unknown node, ambiguous reference, or unsupported construct is a block.
6. EXPLAIN is a database-derived planning boundary. Missing estimates, timeout, planner failure, or thresholds exceeded are blocks.
7. Database execution is a defense-in-depth boundary. It must use a least-privilege role, a read-only transaction, local timeouts, bounded fetch, and unconditional rollback.
8. API and audit output are disclosure boundaries. They must not leak secrets, raw internal exceptions, credentials, stack traces, or unapproved SQL.

Threats to block include:

- Prompt injection asking the model to ignore instructions or disclose system prompts.
- Multi-statement SQL such as `SELECT ...; DROP TABLE ...`.
- DDL and DML, including `CREATE`, `ALTER`, `DROP`, `TRUNCATE`, `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `UPSERT`, and `REPLACE`.
- Writable CTEs and DML with `RETURNING`.
- `SELECT INTO`, `COPY`, `CALL`, `DO`, `EXECUTE`, transaction control, session changes, grants, revokes, and security-definer behavior.
- Locking clauses such as `FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, `FOR KEY SHARE`, `NOWAIT`, and `SKIP LOCKED`.
- Catalog, internal-schema, audit-table, or non-allowlisted schema access.
- Unknown, ambiguous, or hallucinated table and column references.
- Unsafe or expensive functions such as sleeps, advisory locks, file access, network access, or extension-dependent helpers not explicitly allowed.
- Excessive result size, excessive estimated rows, excessive estimated cost, deep nesting, or planner/execution timeouts.
- Error, audit, or result leakage of sensitive values.

## SQL Parsing and AST Strategy

Use a real SQL parser that supports PostgreSQL syntax, with `sqlglot` as the expected starting dependency. Parser selection must be verified against the adversarial test matrix before execution is enabled.

Required parser behavior:

- Parse with PostgreSQL dialect.
- Require exactly one parsed statement and full consumption of the SQL string.
- Reject parser warnings, best-effort recovery, unknown nodes, unsupported expressions, or dialect fallbacks.
- Preserve enough AST detail to detect statement type, CTE bodies, table expressions, joins, projections, LIMIT, functions, and locking clauses.
- Convert parser exceptions into stable internal policy findings and public blocked-query errors.

Do not use string matching or keyword matching as the authorization mechanism. Keyword matching cannot detect semantics hidden in nested CTEs, comments, quoted identifiers, string literals, dialect-specific syntax, DML with `RETURNING`, `SELECT INTO`, or lock clauses, and it can false-positive harmless literals. The AST is the source of truth.

## Syntax and Schema-Reference Validation

Validation order must be deterministic and fail closed:

1. Normalize provider SQL for parser input without altering semantics.
2. Parse as PostgreSQL and require exactly one statement.
3. Validate top-level and nested AST node families before identifier validation.
4. Reject non-SELECT statements and unsupported SELECT variants.
5. Traverse all CTEs, subqueries, set operations, joins, projections, predicates, ordering, grouping, windows, and function calls.
6. Extract table aliases and table references from the AST, not provider metadata.
7. Resolve schemas, tables, and columns against the current `SchemaCatalog`.
8. Validate that all referenced schemas are in `settings.schema_introspection_schemas`.
9. Reject PostgreSQL internal schemas, project audit tables, and any object omitted by schema introspection filters.
10. Resolve unqualified table names only when they are unique within the allowed schemas.
11. Resolve unqualified columns only when they are unambiguous within the visible relation scope.
12. Reject unknown identifiers, ambiguous identifiers, wildcard projections except `count(*)`, and provider-declared identifier lists that disagree with AST extraction.
13. Apply LIMIT policy and generate canonical bounded SQL.
14. Reparse and re-run every AST and schema policy on rewritten SQL.
15. Run EXPLAIN only after the second validation pass succeeds.

The schema validator must use `backend/app/domain/schema.py` and `backend/app/domain/schema_catalog.py` domain objects. It must not parse prompt text or trust `SQLGenerationResult.tables_used` or `SQLGenerationResult.columns_used` for authorization.

## Policy Rules

Implement guardrails as composable policy rules rather than one large conditional. The expected interface should be close to:

```python
class SQLPolicyRule(Protocol):
    def evaluate(self, context: SQLPolicyContext) -> tuple[SQLPolicyFinding, ...]: ...
```

`SQLPolicyContext` should include original SQL, parsed AST, current `SchemaCatalog`, settings, extracted identifiers, and rewrite state. `SQLPolicyFinding` should include a stable internal code, public-safe code, severity, message, and optional redacted metadata.

Required rules:

- `SingleStatementRule`
- `SelectOnlyRule`
- `NoDDLRule`
- `NoDMLRule`
- `NoTransactionOrSessionRule`
- `NoWritableCTERule`
- `NoSelectIntoRule`
- `NoCopyCallDoExecuteRule`
- `NoLockingClauseRule`
- `AllowedSchemaRule`
- `KnownIdentifierRule`
- `NoAuditOrInternalObjectRule`
- `FunctionAllowlistRule`
- `LimitPolicyRule`
- `MaxDepthRule`
- `ExplainThresholdRule`

Every rule must be fail-closed. A rule that cannot classify a node, identifier, or expression must return a blocking finding.

## Result Size, LIMIT, and Nesting

Guardrails must bound results before EXPLAIN and execution:

- Add settings for default row limit, maximum row limit, and maximum fetch rows. Initial defaults should be `sql_guardrail_default_limit = 100`, `sql_guardrail_max_limit = 500`, and `sql_execution_max_rows = 500`.
- If the top-level SELECT has no LIMIT, inject the default LIMIT using AST rewrite.
- If a literal top-level LIMIT is greater than the maximum, lower it to the maximum.
- Reject `LIMIT ALL`, negative limits, non-literal dynamic limits, provider parameters, or syntax where the parser cannot prove the effective bound.
- Preserve existing smaller literal limits.
- Reparse and revalidate rewritten SQL before EXPLAIN.
- Track whether a LIMIT was injected or capped and include this in validation metadata and audit logs.
- Add `sql_guardrail_max_subquery_depth`, default `5`, and `sql_guardrail_max_ast_depth`, default `30`.
- Reject CTE/subquery nesting deeper than the configured maximum, including nested CTEs and derived tables.

LIMIT injection does not make unsafe SQL safe; it is only applied after structural SELECT-only validation passes and before the second validation pass.

## EXPLAIN-Based Cost and Row Limits

Before execution, run:

```sql
EXPLAIN (FORMAT JSON, COSTS TRUE, VERBOSE TRUE) <validated_sql>
```

Do not use `ANALYZE` for generated SQL. EXPLAIN must run in the same safety posture as execution: read-only role, transaction, and local timeout.

Add configurable thresholds:

- `sql_guardrail_explain_timeout_ms`, default `1000`.
- `sql_guardrail_max_plan_rows`, default `50000`.
- `sql_guardrail_max_plan_total_cost`, default `100000`.

Reject when:

- EXPLAIN errors or times out.
- JSON shape is missing or malformed.
- Estimated rows or total cost are missing.
- Estimated rows or total cost exceed configured thresholds.
- The plan references objects outside the already validated identifier set.

The public API must report a stable blocked outcome such as `sql_guardrail_plan_too_expensive`, not raw planner output.

## Database Execution Requirements

Generated SQL must execute only after successful AST validation, schema validation, LIMIT rewrite/revalidation, and EXPLAIN threshold validation.

Execution requirements:

- Use the configured read-only role, defaulting to `text_to_sql_reader`.
- Open a transaction explicitly and make it read-only with `BEGIN READ ONLY` or SQLAlchemy equivalent.
- Set local execution controls before EXPLAIN and execution:
  - `SET LOCAL statement_timeout = <settings.database_statement_timeout_ms>`
  - `SET LOCAL idle_in_transaction_session_timeout = <settings.database_statement_timeout_ms>`
  - `SET LOCAL lock_timeout = <new sql_execution_lock_timeout_ms setting>`
- Execute the validated rewritten SQL only.
- Fetch at most `sql_execution_max_rows + 1` rows to detect truncation.
- Return at most `sql_execution_max_rows` rows and include truncation metadata.
- Always rollback after EXPLAIN and after execution, including successful reads.
- Never commit a generated-query transaction.
- Convert database errors to stable public errors and redacted audit findings.

Strengthen `database/init/20_readonly_role.sh` during implementation:

- Add `ALTER ROLE :"readonly_user" SET default_transaction_read_only = on`.
- Keep `search_path = commerce, pg_catalog`.
- Do not grant access to audit schemas or future operational tables.
- Preserve only `CONNECT`, `USAGE` on allowed schemas, and `SELECT` on allowed business tables.

## Failure Behavior and Error Contracts

All validation and execution failures must fail closed. No partial execution is allowed after a blocking finding.

Recommended public error/result codes:

- `sql_guardrail_parse_error`: SQL cannot be parsed exactly as one supported PostgreSQL statement.
- `sql_guardrail_multiple_statements`: more than one statement is present.
- `sql_guardrail_non_select`: top-level or nested statement is not an allowed SELECT.
- `sql_guardrail_mutation_blocked`: DDL, DML, writable CTE, `SELECT INTO`, transaction control, or role/privilege operation found.
- `sql_guardrail_locking_blocked`: locking clause found.
- `sql_guardrail_schema_error`: unknown, ambiguous, internal, audit, or non-allowlisted object found.
- `sql_guardrail_limit_error`: LIMIT cannot be proven or rewritten safely.
- `sql_guardrail_complexity_error`: nesting or AST depth exceeds limits.
- `sql_guardrail_plan_too_expensive`: EXPLAIN cost or row thresholds exceeded.
- `sql_execution_timeout`: execution timed out.
- `sql_execution_error`: read-only execution failed without safe details.

API behavior options:

- Preserve `POST /v1/query/draft` as generation-only but add a `blocked_query` result when generated SQL fails guardrails.
- Add a new `POST /v1/query/run` endpoint that returns `query_result`, `clarification_required`, or `blocked_query`.

The implementation must choose one API surface in the first guardrail implementation prompt and document it. In either case, public responses must include `request_id`, stable code, public-safe message, and redacted metadata. They must not include raw parser exceptions, raw PostgreSQL errors, credentials, provider stack traces, or unapproved rewritten SQL.

## Audit Logging

Add structured audit logging for each guardrail decision and execution attempt. The log event must include:

- `request_id`
- outcome: `approved`, `blocked`, `executed`, `failed`
- stable policy codes
- provider name and model name when available
- extracted table and column identifiers after AST validation
- whether LIMIT was injected or capped
- effective LIMIT
- EXPLAIN estimated rows and total cost when available
- execution duration and row count when available
- normalized question hash and SQL hash

Audit logs must not include:

- API keys, database passwords, or full database URLs
- raw prompts
- raw provider exception details
- raw PostgreSQL exception details
- full rejected SQL by default
- sensitive row values

Audit objects must not be visible to generated SQL. If persistent audit tables are later added, keep them outside `commerce` or match existing audit-table exclusion rules, and do not grant the generated-query role access.

- Allows read-only CTEs.

- Rejects wildcard projections except `count(*)`.

Property-style tests:

- Random whitespace, comments, casing, and quoted identifiers must not bypass policy.

- Any SQL containing multiple parseable statements must be rejected.

## Safety and Rollback

Safety properties that must be proven at the application layer:

- Only one fully parsed PostgreSQL statement can proceed.
- Only read-only SELECT AST structures can proceed.
- DDL, DML, writable CTEs, transaction/session control, `COPY`, `CALL`, `DO`, `EXECUTE`, `SELECT INTO`, and locking clauses are blocked.
- Every referenced schema, table, and column is extracted from the AST and validated against the current schema catalog.
- LIMIT bounds are present after rewrite and verified by a second parse/validation pass.
- Queries over nesting, row, cost, or timeout thresholds are blocked.
- Errors and audit logs are redacted.

Safety properties that must be proven at the database layer:

- Generated SQL connects as the read-only role.
- The role cannot write or modify schema even if application validation fails.
- The role defaults to read-only transactions.
- Runtime transactions are explicitly read-only.
- Timeouts apply to EXPLAIN and execution.
- Successful and failed generated-query transactions rollback.
- Audit/internal tables are not accessible to the generated-query role.

Rollback strategy:

- Each implementation stage must be separately reviewable and reversible.
- If parser correctness is uncertain, block execution rather than adding string-based exceptions.
- If EXPLAIN or database-role proof fails, keep `/v1/query/draft` generation-only and do not expose execution.
- If API wiring causes regressions, revert to the existing draft-only behavior in `backend/app/api/query.py`.
- If database privilege changes regress local setup, revert `database/init/20_readonly_role.sh` and keep application execution disabled until privileges are fixed.

## Completion Criteria

Implementation is complete only when:

- The backend never executes provider SQL unless AST parsing, policy validation, schema validation, LIMIT rewrite/revalidation, and EXPLAIN thresholds all pass.
- The design fails closed for parser errors, unsupported syntax, unknown AST nodes, unknown identifiers, ambiguous identifiers, planner failures, threshold violations, and database errors.
- The implementation does not rely solely on keyword matching.
- Generated-query execution uses the read-only role, read-only transaction, local timeouts, bounded fetch, and unconditional rollback.
- Unit, property-style, adversarial, and integration tests cover the matrix above.
- Public API errors and audit logs are stable and redacted.
- `make check` passes.
